# 05｜接口与千牛右侧插件

## 1. 四个接口

### 分析案例

`POST /api/cases/analyze`

输入：`CaseInput`  
输出：`ExtractedJourney + AccountabilityState`

### 评估动作

`POST /api/actions/evaluate`

输入：`AccountabilityState + PreparedAction`  
输出：`DecisionResult`

### 人工确认解决路径

`POST /api/resolutions/approve`

输入：Case ID、解决路径、承诺生效确认与人工修改  
输出：更新后的 `AccountabilityState`，包含服务进度回执

### 推送物流事件

`POST /api/events/shipment`

输入：Case ID、事件类型和事件时间  
输出：更新后的责任状态、催办候选与消费者主动通知草稿

接口数量不因服务进度回执增加；回执是账本的派生视图。

## 2. 千牛布局约束

赛事说明中的右侧辅助区是插件目标区域。Competition MVP 按约 360–420px 的窄栏设计，并保留中部聊天区和底部客服输入区。插件不覆盖消费者对话，也不要求客服跳转独立系统。

## 3. 第一屏只回答三个问题

### 已经知道什么

- 粉底液正装、商品货号与订单。
- 泵头损坏图片已提交，客服已确认包装破损。
- 换货工单已创建，承诺 48 小时内发出。

### 现在最不能做什么

- `发送已暂停：不要再次索取相同破损图片。`

### 下一步直接做什么

- 主按钮：`查询补发进度`。
- 次按钮：`生成解决回复`。
- 条件按钮：`提交仓库催办`。

完整旅程、AI 抽取、承诺分类、证据观察和规则来源全部折叠。

## 4. 两个连续界面状态

### 动作前状态

顶部突出 `INTERVENE / ALLOW / HUMAN_REVIEW`、一句中文原因和两个直接动作，避免客服阅读产品论文。

### 人工确认后状态

第一屏转为服务进度回执和责任倒计时，继续显示“消费者无需操作”、下次检查时间和异常补救策略。

## 5. 消费者端表达

消费者不看到内部产品术语。服务进度回执以聊天消息或消息卡片形式发送，只回答：已收到什么、正在做什么、何时更新、未完成时如何处理、是否需要消费者操作。

## 6. 轻量管理区

不开发独立 BI 大屏。可展示的赛事 Mock 数据事实包括：

- 五类工单合计 80 条。
- 28 条工单当前不是“已完结”状态。
- 4 条补发换货工单进行中。
- 5 条物流工单处于工单组或仓库处理状态。
- 4 条不良反应工单处于待处理或处理中。

“重复索证风险”只能来自人工标注的压力测试案例，必须标记为测试假设，不能写成赛事数据发现。

## 7. 交互约束

- 1366×768 下无需滚动即可看到判断、原因和首要动作。
- 警告只在高价值动作前出现，避免提醒疲劳。
- 颜色不作为唯一状态表达。
- 默认不展示 JSON、置信度小数或内部责任人姓名。
- “模拟数据”标识固定可见一次，不反复打断演示。
