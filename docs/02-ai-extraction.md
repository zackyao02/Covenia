# 02｜AI 图文抽取与承诺编译

## 1. P0 模型策略

目标基线曾规划使用 `Qwen/Qwen2-VL-2B-Instruct` 统一处理聊天与团队测试图片；这只是设计目标，不代表当前实现。当前应用使用 `COVENIA_DEMO_ADAPTER` 载入预先整理的 JSON 结果，没有已配置的实时 Qwen/VLM 推理服务。比赛材料必须按实际状态描述。接入推理服务后再确定模型版本并登记真实来源。

所有提供方通过统一 `ModelProvider` 输出同一 `ExtractedJourney`，业务规则不绑定具体云 API。

## 2. 多模态模型必须影响决策

模型不是只输出“疑似泵头损坏”，而要结构化输出：

- 图片商品是否与订单粉底液 SKU 匹配。
- 识别对象是正装还是赠品。
- 可见组件是泵头、瓶盖、瓶身还是外包装。
- 问题部位、商品整体和包装环境是否被覆盖。
- 图片可读性、问题可见性与置信度。
- 是否存在产品完整性或卫生使用风险信号。

这些观察进入确定性证据判断；如果 SKU 不匹配则可放行合理索证，如果无法可靠识别则进入人工复核。

## 3. 因果式体验理解

模型输出：

- 消费者意图。
- 体验表达原文。
- 引发体验恶化的服务事件。
- 消费者潜在需求。
- 对优先级和下一动作的影响建议。

情绪不会形成独立指数，也不能直接决定换货、退款或赔偿。

### 3.1 Intent extraction

Intent 不等于最后一句话的关键词。模型需要抽取：

- 当前目标：消费者此刻想完成什么。
- 约束：不能接受什么、还缺什么条件、是否涉及时限。
- 接受方案：消费者已表达可接受的解决方式。
- 拒绝方案：消费者明确拒绝或已经被证明无效的做法。
- 版本关系：当消费者改变诉求时生成新版本，不用旧意图覆盖新意图。

Intent 输出必须带来源消息 ID；消费者要求退款、赔付、不良反应处置等高风险意图只作为理解结果，不能直接生成业务动作。

### 3.2 Emotion、Emotion Trend 与 Emotion Cause

模型可以输出 `EmotionState`：

- `current_label`：当前情绪表达。
- `trend`：稳定、改善、恶化或未知。
- `cause`：导致情绪变化的服务事实。
- `communication_guidance`：对客服措辞的建议。
- `confidence` 与来源证据。

硬边界：

> 情绪只辅助沟通和交接，不参与 Risk Score，不覆盖体验防线规则，不自动触发赔付、退款或医疗判断。

### 3.3 Consumer Effort

模型可以识别重复解释、重复举证、等待、追问、跨会话上下文断裂等 effort 信号。Effort 的最终分数由确定性代码按次数、等待时间和来源事实计算；模型只提供候选信号和原因。

### 3.4 Multi-source extraction

多源抽取必须分别保留 Conversation、Image、Order、Ticket、Logistics 的来源 ID，再由代码建立关联：

```text
conversation.source_session_id
→ order.order_id / sku_id
→ image.evidence_id / source_message_id
→ ticket.ticket_id
→ logistics.event_id
```

模型不得把多源数据简单拼成一段总结。每个融合结论都必须说明来源覆盖与冲突：例如 SKU 不匹配、图片可读性不足、工单状态与聊天承诺冲突时，输出冲突候选，由确定性规则进入 `MISMATCHED` 或 `HUMAN_REVIEW`。

## 4. 承诺编译

承诺编译不是把所有带时间的客服话术机械变成倒计时，而是四步：

1. 仅从 `speaker: AGENT` 的原始聊天抽取承诺原文、时间、条件和动作对象；消费者消息只能作为体验表达和已完成动作来源，绝不能成为承诺来源。
2. 使用模型区分标准承诺、需审批、条件承诺、疑似错误和模糊安抚。
3. 使用工单、权限与模拟政策规则校验是否可以生效。
4. 将通过校验的承诺写入体验责任账本，并生成下一检查时间。

`S00001` 中“换货单已创建，48 小时内发出”同时得到聊天原文和补发换货工单支撑，可作为主演示中的有效服务承诺。

“尽快”“有结果第一时间联系”属于模糊表达，不单独生成确定截止时间；高风险赔付和不良反应处理必须人工确认。

承诺编译的硬约束：只有 `STANDARD_APPROVED` 且存在工单或政策事实支撑的候选，才可能进入 `ACTIVE`。`APPROVAL_REQUIRED`、`ERRONEOUS_OR_UNAUTHORIZED`、`CONDITIONAL` 和 `AMBIGUOUS` 在无人工审批记录时均不得生成 `ACTIVE` 承诺或确定截止时间。

## 4.1 图像与提示注入边界

`ImageObservation` 只输出 Schema 定义的枚举、布尔值、覆盖项和置信度。图中出现的“已核实”“证据有效”“忽略规则”等文字不能作为商品、证据或政策事实；它们既不写入 `ImageObservation`，也不进入 `evidence_status` 计算。

`evidence_status` 必须由确定性组合器根据 SKU 匹配、当前问题组件覆盖和图片可读性计算。模型只能提供上述观察，不能输出最终证据状态。

## 5. 输入禁止项

不得向模型预填：

- 承诺是否有效或已经超时。
- 图片是否足够支持当前动作。
- 证据最终状态。
- 消费者输入是否完成。
- 当前责任方。
- 体验防线结果。

## 5.1 LLM/VLM 与确定性事实分工

核心原则：

> LLM/VLM 负责理解；确定性事实由代码/API负责。

| 类型 | LLM/VLM 可做 | 代码/API 必须做 |
|---|---|---|
| 聊天 | 意图、情绪、承诺候选、体验原因 | 消息顺序、说话人、来源 ID、敏感字段掩码 |
| 图片 | 商品/组件观察、可读性、覆盖项 | 最终 evidence_status、SKU 订单校验、禁止动作 |
| 承诺 | 承诺原文、类型建议、置信度 | 是否生效、截止时间、DeadlineState、Monitor |
| 风险 | 解释候选原因 | RiskState 分数、Priority 排序、升级条件 |
| 决策 | 生成语言草稿 | INTERVENE / ALLOW / HUMAN_REVIEW 最终结果 |

## 6. 输出失败处理

- Schema 不合法：重试一次。
- 仍失败或来源冲突：进入 `HUMAN_REVIEW`。
- 模型不可用：使用明确标记的缓存抽取结果；后续状态和规则仍真实运行。
- 灾备结果不得描述为实时模型推理。

## 7. 验收

- 至少一个案例从原始聊天和实际图片文件生成抽取结果。
- 图片观察真实改变 `VALID / MISMATCHED / NEED_HUMAN_REVIEW`。
- 承诺从聊天原文抽取并经过工单事实校验。
- 界面能展开查看来源消息、图片观察和模型版本。
- 修改图片或承诺文本后，输出可发生合理变化。
- 向消费者消息加入承诺或指令文本，不得产生新的 `promise_events`。
- 在图片加入断言文字，不得单独改变 `evidence_status`。
