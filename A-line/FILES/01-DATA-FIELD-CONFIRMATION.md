# A-01｜数据字段与案例确认

对应任务：`TEAM_AND_TIMELINE.md` 9/2–9/4「确认数据字段与案例」
数据源：`data/tianchi-track1-mock-data.xlsx`（官方 Mock 数据，8 个工作表，其中「数据说明」不是运行输入）
核对日期：2026-09-10
核对方式：按字符串逐单元格读取全部 8 表，与 `README.md`、`docs/00-product-p0.md` 第 3 节公开口径逐项比对

---

## 1. 目的

本文件回答四个问题，供 B 线写导入层、C 线渲染右栏、D 线做验收时直接引用：

1. 赛事工作簿里到底有哪些字段，每张表的粒度是什么。
2. 哪些字段是主键、哪些是外键，表和表之间怎么关联。
3. 每个字段进系统时要变成什么类型，哪些字段不能按数字读。
4. 数据本身有没有坑，坑在哪里，处理决定是什么。

本文件只描述事实与导入约定，不定义产品行为。产品范围以 `PRODUCT-FREEZE.md` 为准，接口以 `schemas/` 与 `docs/05-api-and-ui.md` 为准。

### 2.3 表粒度确认

| 工作表 | 一行代表 | 唯一键 | 一个会话最多几行 |
|---|---|---|---:|
| 聊天记录 | 一条消息 | `message_id` | 10（实测最多 10 条） |
| 订单 | 一笔订单 | `订单号` | 1 |
| 五类工单（各表） | 一张工单 | `工单号` | 1（五表合并后也是 1） |

**结论：会话是整个数据集的关联中枢，`会话ID → 订单 → 工单` 是三段式一对一链路。** 这一点与 `docs/00-product-p0.md` 第 3 节和「数据说明」表中的关联关系描述完全一致。

## 4. 关联规则确认

### 4.1 三段式关联链

```text
聊天记录.会话ID ──1:1──> 订单.会话ID ──1:1──> 五类工单.会话ID
        └─ 校验 ─> 聊天记录.关联订单号 = 订单.订单号
        └─ 校验 ─> 聊天记录.关联工单号 = 工单.工单号
        └─ 校验 ─> 订单.订单号        = 工单.关联订单号
```

与「数据说明」表给出的关联关系完全一致，实测覆盖率：

| 校验项 | 结果 |
|---|---|
| 每张工单的 `关联订单号` 都能在订单表命中 | **80 / 80，缺失 0** |
| 每张工单的 `会话ID` 都能在聊天记录命中 | **80 / 80，缺失 0** |
| 每个有订单的会话，其 `关联订单号` 与订单表一致 | **0 处冲突** |
| 每条带 `关联工单号` 的消息，工单号都在工单表命中 | **0 处冲突** |
| 存在一个会话多笔订单的情况 | **0 个** |
| 存在一个会话多张工单的情况 | **0 个** |

### 4.2 关联优先级（与 `docs/01-core-contracts.md` 第 1 节一致）

1. 首选 `会话ID`：连接聊天、订单与五类工单。
2. 其次 `关联订单号`：做订单一致性校验。
3. 再次 `关联工单号 / 工单号`：连接当前服务动作。
4. `买家昵称` 只用于辅助核对，**不作为唯一主键**（93 个昵称对应 113 笔订单，存在一人多单）。

### 4.3 没有订单的会话

138 个会话中有 **25 个没有关联订单**（`S00002`、`S00013`、`S00019`、`S00022`、`S00025`、`S00036`、`S00041`、`S00067`、`S00069`、`S00073`、`S00080`、`S00083`、`S00086`、`S00091`、`S00092`、`S00095`、`S00113`、`S00134`、`S00140`、`S00151` 等），全部是产品咨询、会员咨询类售前会话。

## 5. 导入契约（给 B 线的强制约定）

### 5.1 类型规则

| 规则 | 适用字段 | 原因 |
|---|---|---|
| **一律按字符串读** | `订单号`、`工单号`、`物流单号`、`问题包裹物流单号`、`补发物流单号`、`原订单物流单号`、`退货物流单号`、`退款编号`、`message_id`、`关联订单号`、`关联工单号` | 19 位订单号超出 Excel 双精度整数可精确表示范围（2^53−1 ≈ 9.007e15），按数字读会变成 `6920185815517983000` 或 `6.92E+18`，直接破坏跨表关联 |
| 按整数读 | `消息序号`、`数量`、`年龄` | 值域小且为序号/计数 |
| 按 decimal 读，并做两位小数规整 | `单价(元)`、`实付金额(元)`、`退款金额(元)`、`订单实付(元)` | 原始值存在 `8.8000000000000007` 一类浮点表示，直接展示会出现脏数据 |
| 按 datetime 读，补 `+08:00` | 所有 `*时间` 字段 | 源数据均为 `yyyy-MM-dd HH:mm:ss` 本地时间，无时区信息；契约要求 `date-time` |
| 按 boolean 读 | `is_target_buyer_message`、`客诉加急`、`是否异常`、`是否就医` | 源值 `1/0`、`是/否` |
| 空字符串与空单元格统一为 `null` | 全部字段 | 当前工作簿空值均为真空白，无 `''` 混用（已核对） |

### 5.2 归一规则

| 归一目标 | 来源 | 映射 |
|---|---|---|
| `speaker` | `角色` | 买家→`CONSUMER`；客服→`AGENT`；系统推送→`SYSTEM` |
| 工单 `status` | `工单状态` 或 `任务状态` | 原样保留中文值，不做语义改写（`进行中`、`处理中`、`工单组处理`、`仓库处理`、`待处理`、`已完结`） |
| `ticket_type` | 来源表 | 补发换货工单→`REPLACEMENT`；线下打款工单→`OFFLINE_PAYMENT`；物流工单→`LOGISTICS`；不良反应工单→`ADVERSE_REACTION`；售后退货工单→`RETURN` |
| `source_sheet` | 来源表名 | 直接用中文表名 |
| `item_role` | `赠品` 列 | 同 SKU 出现在 `赠品` 列→`GIFT`；否则→`PRIMARY`；本数据集无 `BUNDLE_COMPONENT` |
| `source_kind` | 数据来源 | 赛事工作簿→`COMPETITION_MOCK`；团队扩充→`DEMO_AUGMENTATION` |

### 5.3 脱敏规则（对齐 `MODEL_GOVERNANCE.md` 与 `PRODUCT-FREEZE.md` P0-9）

进入 Prompt 前必须掩码，并统计 `pii_masked_count` 写入治理记录：

| 字段 | 处理 |
|---|---|
| `收货省`、`收货市` | 整字段掩码；仅保留「是否同省」一类的布尔派生值 |
| `支付宝实名`、`支付宝账号` | 整字段掩码（源数据本身已部分脱敏，仍需二次掩码） |
| `不良反应工单.症状描述`、`不适部位`、`年龄` | 掩码为最小化占位表达（如「面部不适，已就医」），不发送原始描述 |
| 聊天文本中的手机号 | 消息级正则掩码（实测 48 条消息出现手机号或「支付宝」表述，集中在打款类会话） |
| 聊天文本中的收货地址 | 消息级掩码（实测 1 条消息含完整地址：`S00028` 第 4 条） |
| `买家昵称`、`发送方`、`处理人`、`发货仓库`、`发货仓`、`支付宝账号` | 不进入 Prompt，也不进入消费者可见视图 |

### 5.4 来源标签规则

每个字段在导入结果中携带来源三元组 `(source_sheet, source_row, source_key)`，用于 `ExtractedJourney.source_trace` 与 `fact_trace`：

- `source_sheet`：中文表名，如 `订单`、`补发换货工单`。
- `source_row`：数据行号（含表头，表头为第 1 行）。
- `source_key`：该行的业务主键，如订单号、工单号、`message_id`。

`S00001` 的完整来源定位示例见 `02-数据映射表.md` 第 5 节。

### 6.1 结构性检查：全部通过

| 检查项 | 结果 |
|---|---|
| 4 类单号、消息 ID 精度 | 全部保持字符串读取，无精度损失 |
| 主键唯一性（订单号、工单号、message_id） | 无重复 |

| 订单时间链 `下单 ≤ 付款 ≤ 发货` | 113 / 113 通过 |
| 金额自洽 `数量 × 单价 = 实付金额` | 113 / 113 通过 |

| 退款/退货类工单物流单号空值逻辑 | 自洽（仅退款空包裹类不填退货单号） |

### 6.2 发现 1：赠品列与聊天口述不一致（6 例，需在案例标注中显式处理）

聊天中出现「查到您的订单确实包含赠品 X」的表述，但 `订单.赠品` 列并非 X：

| 会话 | 订单表 `赠品` | 客服口述赠品 | 性质 |
|---|---|---|---|
| `S00007` | 测试丝绒唇釉小样1.2g | 测试修护精华小样5ml | **冲突** |
| `S00020` | （空） | 测试修护精华小样5ml | **冲突** |
| `S00027` | 测试丝绒唇釉小样1.2g | 测试发膜体验装30ml | **冲突** |
| `S00035` | 测试护发精油小样10ml | 测试修护精华小样5ml | **冲突** |
| `S00037` | 测试舒缓面霜中样15ml | 测试积雪草修护霜小样10ml | **冲突** |
| `S00090` | （空） | 测试卸妆棉便携装20片 | **冲突** |

另有 3 例属于**合法业务形态而非数据错误**（订单无该赠品，但由会员权益或直播承诺触发）：

`S00115`（会员权益加赠）、`S00153`（会员权益）、`S00159`（会员权益）；以及 3 例**额外安抚赠品**：`S00011`、`S00050`、`S00108`。

**处理决定：**

- `订单.赠品` 是**系统事实，优先级最高**（`docs/01-core-contracts.md` 第 6 节）。
- 客服口述与系统事实不一致时，不得让模型或规则直接认定赠品归属；标记为 `FACT_CONFLICT`，进入 `HUMAN_REVIEW`。
- 本批标注将 `S00007` 与 `S00037` 纳入，作为「系统事实优先」的负例；`S00115` 作为「合法加赠」的正例。二者构成一对判别测试。
- 该发现不改变产品范围，只影响导入层的事实优先级实现。

### 6.3 发现 2：图片路径目录名只能作粗分类线索（3 例不一致）

`image_path` 的目录名是数据集作者给粗分类，但并非总是与消息内容一致：

| 会话 | 路径目录 | 消息内容 | 目录名是否准确 |
|---|---|---|---|
| `S00034` | `live_promise` | 买家「我截图了主播口播的」 | 准确 |
| `S00053` | `live_promise` | 买家在客服索要支付宝账号后回「发你了，几天到？」 | **不准确**（实际是打款信息） |
| `S00055` | `live_promise` | 同 `S00053` | **不准确** |
| `S00029` | `refund_screenshot` | 买家在客服索要支付宝实名与账号后回「信息发你了呢」 | **存疑** |
| `S00038` | `refund_screenshot` | 同类打款场景 | **存疑** |

**处理决定：**

- 路径目录名只登记为 `image_path_category`（粗线索），**不作为 `ImageObservation` 的任何布尔值或枚举证据**，与 `docs/02-ai-extraction.md` 第 4.1 节一致。
- 首批标注中证据覆盖字段的标注级别统一标记为 `PATH_REFERENCE_ONLY`；真实观测量待团队合成图片就绪后由多模态模型回填。
- 这一条同时说明：`synthetic-pattern-card.json` 中「重复索证」只能是人工标注假设，不能由路径名反推。

### 6.4 发现 3：回复文案存在模板化重复（影响留出集设计）

41 个 `scene_minor` 里，大量会话共用同一套客服话术模板（例如「换货-到手破损」3 例、「仅退款-空包裹」3 例、「色号不合适」3 例）。同一模板在不同会话中的用词差异只在称呼和语气词。

**处理决定：**

- 30 例样本必须**按模板分组后跨组抽样**，同一模板在开发集中最多放 2 例，其余放留出集，避免同模板泄漏导致评测虚高。
- 该规则已写入 `03-标注字段定义与标注规范.md` 第 5 节。

### 6.5 发现 4：一处客服自我纠正的承诺（有价值的正例）

`S00023` 第 7 条客服消息为：「…缺少的眼影盘今天加急补发，顺丰到付…不对，是顺丰包邮直发您家哦哦~」

同一句里先出现错误的「到付」再自行更正为「包邮」。

**处理决定：**

- 标注时以**最终生效语义**（包邮）为承诺内容，同时在 `open_questions` 记录该句存在歧义残留。
- 该例进入开发集，用于验证承诺抽取不因句内自我更正而误判为 `ERRONEOUS_OR_UNAUTHORIZED`。

### 6.6 发现 5：无 `已完结` 之外状态定义的映射表

五表状态共 6 个原值（进行中、处理中、工单组处理、仓库处理、待处理、已完结），但赛事文件没有给出状态流转定义。

**处理决定：** 导入层只做归一与保留，不推断流转语义；状态含义由产品侧在 `docs/04-responsibility-loop.md` 的六状态模型内自行映射，映射表由 B 线实现，A 线不新增定义。
