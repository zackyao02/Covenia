## 1. 六条统一验收门槛

| 编号 | 门槛原文 | D 的验收方法 | 证据 | 状态 |
|---|---|---|---|---|
| G-1 | 原始聊天、订单和团队测试图片能够进入同一案例链路，不能只读取预填结论 | 跑 `POST /api/cases/analyze` 传 `case_id`，检查输出里的承诺和图片观察来自原始输入 | 输入 JSON + 输出 JSON 截图各一张 | 待测 |
| G-2 | 模型输出能够改变证据状态、情绪成因或承诺状态，并由规则完成安全判断 | 对比清晰图与模糊图两次运行，看 `evidence_status` 是否真的变化 | 两次响应对照 | 待测 |
| G-3 | 同一规则链能够输出一次拦截、一次放行和一次人工复核 | 跑 `DEMO_001`（`INTERVENE`）、范围变化（`ALLOW`）、模糊图（`HUMAN_REVIEW`） | 三次响应截图 | 待测 |
| G-4 | 人工确认后能够创建服务责任和服务进度回执 | 跑 `POST /api/resolutions/approve`，看 `open_obligation` 与 `service_progress_receipt` 是否同时非空 | 响应 + 界面截图 | 待测 |
| G-5 | 物流事件能够触发责任状态变化；固定动画只能作为灾备展示，不能冒充运行结果 | 跑 `POST /api/events/shipment` 两个分支；核对界面上的状态变化是否来自接口 | 两次响应 + 界面截图 | 待测 |
| G-6 | 所有赛事 Mock 数据、团队扩充数据、真实调研和系统评测都单独标注来源 | 逐屏检查标注；核对演示口播用词 | 界面截图 + 口播稿用词核对 | 待测 |

## 2. 不可突破的产品边界（红线）

| 编号 | 红线 | 检查方式 | 违规后果 | 状态 |
|---|---|---|---|---|
| R-1 | 不自动退款、赔偿、补发、质量定责或医疗诊断 | 检查界面上没有「自动退款 / 自动赔偿 / 自动补发」按钮；`compiled_service_responsibility` 中无 `ACTIVE` 的赔付类承诺 | 直接失去合规资格 | 待测 |
| R-2 | 高风险动作保持人工确认 | `approve` 必须有 `approver_id`，主动通知外发必须标记为草稿 | 严重 | 待测 |
| R-3 | 不把赛事 Mock 说成欧莱雅真实数据 | 界面固定显示「赛事 Mock 数据＋团队压力测试扩充」；口播不使用「欧莱雅真实消费者复联案例」 | 严重 | 待测 |
| R-4 | 不把团队扩充说成原始赛事记录 | 第二次进线、额外图片、评估时间、物流事件都必须带扩充标记 | 严重 | 待测 |
| R-5 | 不宣称接入生产千牛、OMS、WMS、TMS | 界面与文案不得出现「已接入」表述 | 严重 | 待测 |
| R-6 | 缓存抽取结果必须三处同时标注 | 响应 `model_metadata.cached_result` + 界面角标 + 治理记录 | 门 2 失败 | 待测 |
| R-7 | `ground-truth.json` 不得进入模型、状态构建器或体验防线 | 检查请求体与模型输入中无 `expected_*` 字段 | 门 3 失败 | 待测 |
| R-8 | 不给一线客服增加新系统 | 插件不覆盖消费者对话，不要求跳转独立系统 | 中度 | 待测 |
| R-9 | 不新增独立模块、页面或售后场景 | 对照 `PRODUCT-FREEZE.md`「P0 页面」与「明确不做」 | 中度 | 待测 |
| R-10 | 敏感字段先掩码再进模型 | 手机号、收货地址、支付宝账号、就医与不良反应描述 | 严重 | 待测 |

## 3. 外部材料清理红线（提交前）

来源：`docs/07-demo-and-delivery.md` §5。

- 对外材料不出现内部评分、团队昵称、版本争论。
- 不出现预测准确率或未完成治理项。
- 最终 Word 在 Windows Word 导出 PDF 并逐页检查中文、分页和图片。
- 六项 KPI 模板只能标为 `n=1` 匿名业务输入，不能外推为市场结论。
- 询单转化率属售前指标，不纳入本项目效果主张。
