# Covenia 当前产品多角度评审

日期：2026-10-04。目标：比赛可用的千牛售后插件原型。

## 结论

产品有明确的价值方向：把多轮售后中的已有材料、品牌承诺和后续责任关联起来，减少消费者重复解释，让品牌持续跟到兑现。但现在仍存在影响闭环可信度的问题，不能把剩余工作都归为视觉细节。

优先完成三个事项：确认回复不能回退履约状态；回复检查正确理解否定与查询意图；补材料和人工接手两条支线有可观察的模拟后续。然后收拢重复卡片，进行干净环境的独立验收。

## 本轮证据范围

- 阅读当前前后端实现、项目简介、已有验收记录和用户最新截图。
- 阅读本地赛题工作台说明：右侧插件应在不干扰核心聊天流程的前提下提供即时决策辅助和快速操作。
- 使用独立 Python 进程中的本地接口测试客户端复核状态变化和回复分类；模型调用替换为规则降级，未消费 JEV 调用额度，也未修改正在运行的浏览器会话。
- 本轮浏览器控制工具初始化失败，因此没有完成最新版本的全流程点击、键盘操作和多尺寸实机验收。截图与代码能够支持结构判断，不能替代这些验收。
- 本报告为评审，不代表下列问题已修复，也不是最终独立验收通过记录。

## 多角度判断

| 角度 | 当前优势 | 主要不足 | 改进目标 |
| --- | --- | --- | --- |
| 客服使用价值 | 恢复材料、区分商品范围、保留承诺并检查不当回复，适合多轮复杂售后 | 操作仍集中在写回复和确认；真正省掉的查找、催办、交接成本不够直观 | 让插件承担一次可见的上下文恢复、责任跟进和主动更新 |
| 工作流一致性 | 换货分支有揽收、超时补救和送达状态变化 | 再次批准回复能把运输中回退为等待揽收 | 聊天记录更新与履约状态变化分开；只有履约事件推进物流阶段 |
| 对话与交互 | 有推荐回复、发送前检查和重置入口 | 否定词会被误判；顾客模拟最多两轮；补图和转专人缺后续结果 | 给常用客服表达稳定的处理结果；补齐有限但完整的场景状态 |
| 视觉与信息结构 | 青绿色玻璃风格已经形成识别度 | 主状态、回执、聊天回执重复长文；卡片权重接近；多处独立滚动 | 先看懂状态和动作，详细事实按需展开；减少重复，不增加装饰卡片 |
| JEV 与可信度 | 有真实调用路径，新顾客消息可以参与沟通判断，硬规则保留独立责任边界 | 情绪概率未校准，模型对产品的可见作用主要是沟通语气和推荐排序 | 用具体对话依据及建议变化体现作用；独立样本校准后才使用校准结论 |
| 比赛表达与交付 | “品牌不能忘记自己答应过什么”容易记住，符合复杂售后断点 | 功能多但价值证明分散；旧验收材料不能覆盖本轮变更 | 用一条完整主线展示少重复索证、按时更新、异常补救和完成履约 |

## 已复核的高优先级问题

### 1. 再次确认进度回复会回退履约状态

复现顺序：分析 DEMO_001 → 确认查询进度回复 → 写入物流揽收事件 → 再确认查询进度回复。

隔离接口复核结果：首次确认 HTTP 200；揽收 HTTP 200；揽收后里程碑为 `IN_TRANSIT`；第二次确认 HTTP 200；里程碑变为 `AWAITING_CARRIER_PICKUP`。

定位：`backend/main.py` 的 `approve_resolution`，约第 1080 行。批准回复时重新写入履约义务，固定将里程碑设为等待揽收，并重写执行方、义务状态和回执。物流事件维护的另一份阶段状态未随之统一更新。

用户影响：客服已经确认发货，再回复顾客却显示尚未揽收；这会直接削弱“持续跟进责任”的核心承诺。

修复验收：运输中案件确认普通回复后，里程碑、执行方、原履约期限保持一致；允许明确修改下次更新时间并记录审计；重复操作不创建第二项履约责任。覆盖完成履约和逾期补救后的再次回复。

### 2. 回复检查不能可靠理解否定与查询

隔离规则复核：

- “我会先核实换货进度，并主动告知。”被同时识别为进度查询与新增承诺，归入未分类并要求确认。
- “我不能保证明天送达，但会帮您查询物流进度。”被承诺拦截函数判为包含不支持的履约保证。
- “您的问题还未解决，我不会结案。”被识别为结案。

定位：`backend/draft_review.py` 的 `assess_draft` 和 `contains_unsupported_fulfillment_guarantee`。当前关键词识别缺少完整的否定、语义范围及既有履约查询区分。

用户影响：安全回复也被阻止，会增加客服修改成本；推荐、检查与确认三处若解释不一致，用户难以理解怎样才能继续。

修复验收：同一回复在推荐、发送检查、人工确认阶段得到一致分类；区分询问既有状态、承诺一个更新时间、保证一个物流结果；否定的保证和否定的结案不能作为肯定动作处理。不能为了减少误判而放开明确的不当保证。

### 3. 两条支线还没有完整可观察结果

`frontend/src/consumerSimulator.ts` 在 `turn >= 2` 时停止生成顾客回复。有限轮数本身合理，但当前后续状态不足：

- 精华案例：顾客答应补一张照片，但缺少可操作的模拟提交、证据范围更新和继续处理结果。
- 防晒案例：顾客答应等待专人，但缺少模拟接手人、明确更新时间及专人反馈。

用户影响：三个消费者虽然已区分商品和问题，但两条支线仍容易结束在“等你补”“等人工”，评委不易看到插件比回复助手多做了什么。

修复验收：用有限状态的模拟动作补齐结果。补图必须真的改变证据状态；人工接手必须真的写入责任和更新安排。无需让脚本无限聊天，也不能将脚本写成实时自由生成的顾客模型来宣传。

## 视觉与交互收敛

保留用户指定的青绿色玻璃视觉语言，把空间感用于主状态和关键动作。主卡只呈现当前状态、一句原因、一个下一步；时间和责任方紧凑呈现。消费者可见回执在聊天中展示一次，插件侧保留摘要与详情入口，避免把完整话术作为品牌处理动作重复铺开。

JEV 保持辅助层级：让客服先看建议和相关对话依据，再看百分比。保留清楚的“模型判断”含义，百分比不作为准确率或业务收益。无需叠加更多概念解释。

小号文字、推荐按钮、固定回复区和多重滚动需要在较窄窗口实测；不能只凭现有响应式样式认定手机端和键盘操作已验收。已有焦点与减少动效支持是基础，仍需检验是否能完整完成回复、确认、重置与详情查看。

## 让评委看见产品的必要性

建议围绕一个主案例展开：消费者再次催问 → 插件找回已有照片和旧承诺 → 拦截重复索证 → 客服确认责任与主动更新时间 → 模拟到点仍未揽收 → 出现升级安排和主动通知 → 揽收及送达后责任完成。

重点展示每个动作引起的真实状态变化，而不是只展示更多卡片。两个支线分别证明“只补当前商品缺失材料”和“高敏感反馈交给专人并持续跟进”。

如果展示本案贡献计数，应来自实际操作日志，如本轮拦截重复索证次数、已复用材料数量、已确认主动更新时间。不能把这些场景计数替代真实用户效率提升或客诉下降比例。

## 完成顺序

1. 修复状态回退和回复误判，加入针对上述行为的回归验证。
2. 补齐补材料、人工接手两条模拟支线的结果。
3. 精简重复回执、长文和辅助说明，实测常用窗口尺寸及键盘路径。
4. 用重置后的完整演示链路做第三方独立复验，再更新验收文档和交付包。

当前目标是比赛原型。真实千牛渠道、仓库系统和生产持久化不必阻塞这轮比赛交付，但模拟边界需要在交付说明中准确保留。

交互复核另发现已揽收后自动回复仍在询问“是否揽收”。现已将建议回复绑定已记录的物流里程碑，并验证重新打开页面时显示已揽收话术；客服手写草稿不会被事件覆盖。主案再次确认回复仍保持运输阶段，补图与专人两支线已在独立浏览器中点击验证。
